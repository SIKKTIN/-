### 架构总纲


#### 1. 架构目标

让一个功能的规则、状态和行为有明确归属；让调用方只依赖必要的接口；让实现能在不扩散修改的情况下演进。

跨引擎通用首先指组织方式和行为契约通用。若项目采用不同语言，通常需要重新实现代码；不能仅凭目录相同就认定源码可移植。

#### 2. 最小结构

```text
项目入口 / UI / 场景交互
              ↓
       Package 公开接口
              ↓
      业务规则与私有状态
              ↓ 按需使用
     Core 或引擎提供的能力
```

项目入口负责组装实例、连接场景和触发生命周期。它可以直接装配少量 Package，不需要先建立模块扫描器或依赖容器。

#### 3. Package 与 Core

| 判断维度 | Package | Core |
| --- | --- | --- |
| 主要回答 | 这个游戏功能应该做什么 | 多个业务共同需要的机制如何工作 |
| 规则例子 | 作物成熟条件、物品堆叠、任务完成条件 | 事件派发、存档读写调度、诊断 |
| 数据例子 | 作物状态、背包内容、任务进度 | 订阅表、存档槽位索引、调度状态 |
| 修改原因 | 玩法和业务需求变化 | 通用机制、可靠性或平台接入变化 |
| 不应出现 | 任意访问其他包私有状态 | 特定作物、武器、任务的判断分支 |

Combat 即使被玩家、敌人、陷阱共同调用，仍可能是 Package，因为伤害和战斗规则属于业务。一个 Clamp 数学函数即使全项目使用，也可以只是工具函数。

#### 4. 通用规则

1. 每段可变业务状态有明确所有者；其他包只能通过其公开契约查询或修改。
2. 一个包可以依赖另一个包的公共接口，依赖关系明确且避免循环。
3. 公共接口承诺行为，不泄露调用方不需要知道的内部组织。
4. 查询不产生可观察的业务修改，命令说明是否发生变化及失败后状态。
5. 事件用于通知事实，不承担需要结果的隐式命令。
6. 初始化、运行和清理责任明确；没有对应需求就不增加相应回调。
7. 外部配置进入业务前验证，运行状态与默认配置分开。
8. 失败可观察，不把缺失、非法输入、无变化和执行失败都混成同一个含糊结果。

#### 5. 通用不等于必选

框架不要求所有数据走一个 DataCore，也不要求所有包都拥有数据库、事件、存档和 Tick。

以下内容作为扩展使用：保存与迁移、集中数据管理、自动装配、网络通信、复杂跨包提交。对简单单机项目，直接调用和局部状态往往足够。

框架也不要求每一次引擎调用都经过自建接口。可复用规则尽量少依赖引擎，具体场景与表现可以采用引擎惯用结构。只有出现替换实现、隔离副作用或独立测试需求时，再抽取接入边界。

#### 6. Package 的粒度

按独立规则和修改原因划分，而不是按每个实体或每个界面划分。

- 推荐：Inventory 管理不同容器实例；Planting 管理不同地块与作物实例。
- 通常不推荐：每株作物创建一个 Package，每个背包格子创建一个 Package。
- UI 可以按页面组织；业务包按领域组织；两者不要求一一对应。
- 对高频批量计算，允许包内部使用数组、组件或目标引擎的数据导向方式，不强制每个对象一次门面调用。

#### 7. “独立”不等于“随时可卸载”

一个 Package 的职责独立，不代表它不依赖任何业务，也不代表可以在运行中任意关闭。是否可选、何时可关闭、关闭后数据如何保留，应在项目需要模块开关时明确设计。

GameCreator 的故事编排、地图设计等编辑模块与游戏运行时 Package 是不同层次。编辑内容可以由多个运行时包协作使用。

#### 8. 判断新代码放在哪里

| 问题 | 归属建议 |
| --- | --- |
| 它描述具体玩法或领域规则吗 | 对应 Package |
| 它是无状态的通用计算吗 | 工具函数或现有标准库 |
| 它是跨业务统一机制吗 | 评估 Core |
| 它是输入、显示或场景对象绑定吗 | 表现或引擎接入部分 |
| 它是可调整参数吗 | 配置，交所属业务验证 |
| 它是源码可重建的索引吗 | 启用生成扩展后的生成目录 |

暂时无法证明需要公共机制时，优先保留在拥有规则的业务中，再根据真实重复提取。

### Package 组织与公共接口


#### 1. 最小要求

每个包应能够回答：负责什么、不负责什么、如何调用、持有哪些状态、依赖谁、何时创建和释放。

最小逻辑组成只有职责说明、公共入口和实现。文件可以合并，不要求必有 Meta、Data、Query、System 或 Tests 目录。

```text
Packages/Planting/
  README.md
  Planting.<语言扩展名>     # 简单包可在一个文件中实现公开方法和私有状态
```

#### 2. 规模增长后的拆分

```text
Packages/Planting/
  README.md
  Public/                  # 公开入口、结果类型和事件契约
  Query/                   # 只读查询
  System/                  # 修改与业务流程
  Data/                    # 私有状态、结构、默认值和校验
  Tests/                   # 或放在项目统一测试目录
```

按需增加目录。`System` 在这里表示业务操作实现，不要求采用 ECS，也不意味着所有 System 每帧执行。Model、Handler 等名称只在项目确有对应责任时使用。

#### 3. 公共入口

Registry / Facade 代表一个逻辑边界，不强制一个巨大文件。公开类型可以由多个文件提供，但调用方不需要知道包内部 Query 和 System 的目录。

公开方法需要说明：

| 信息 | 示例 |
| --- | --- |
| 作用对象与输入 | Water(plotId) |
| 结果 | 已浇水、已经浇水、地块不存在、不能浇水 |
| 数据影响 | 修改所选地块的浇水状态 |
| 失败状态 | 本命令失败时不改变地块 |
| 同步性 | 本例同步执行 |
| 生命周期前提 | 当前种植实例已创建且未释放 |

语言支持静态类型时优先使用类型检查。不为了统一接口而把所有方法改成字符串名、任意字典和运行时反射。

#### 4. Query 与命令

```text
Planting.GetPlotView(plotId)     # 查询：返回展示需要的值
Planting.Water(plotId)           # 命令：执行规则并返回结果
```

Query 可以有不影响业务的内部缓存，但不得发奖、推进时间、修改任务进度或把查询当作初始化玩家状态的隐蔽入口。

命令先验证再修改。若命令允许部分完成，必须明确返回实际完成范围；不允许出现“返回失败但调用方不知道已经扣了部分资源”的行为。

#### 5. 数据边界

- 包可以直接持有自己的实例状态，不必中央注册。
- 返回集合时使用值、只读视图或快照，避免调用者通过引用绕过接口写入。
- 高性能路径可以采用受控只读借用等语言机制，但要明确寿命和禁止修改规则。
- 包内部字段名不是天然公共协议；存档与网络需要时另行定义稳定表示。

#### 6. 包之间合作

允许 A 直接依赖 B 的公开接口，例如 Planting 在需要容量信息时查询 Inventory。依赖通过构造、初始化参数或明确的语言模块导入体现。

当一个操作同时协调多个独立包且放在任何一方都会形成循环时，可由更上层的业务流程协调。例如“收获作物”流程明确调用 Planting 和 Inventory。小项目可以是一个清晰函数，不必立刻建立一个大型编排框架。

协调者也不拥有参与包的内部数据，不能替它们直接写字段。

#### 7. README 建议模板

```text
职责：
不在范围内：
公共查询：
公共命令及结果：
私有数据与有效范围：
依赖：
创建与释放：
可选扩展：
关键验收案例：
已知限制：
```

没有存档、事件或更新需求时，直接写“不使用”，不创建空文件占位。

### Core 边界与公共机制


#### 1. 提取条件

一个能力进入 Core，应有跨业务使用的实际需求，并且需要统一的行为、资源管理或生命周期。不能仅因名字听起来基础、被多个文件调用，就放入 Core。

常见候选包括事件派发、保存调度、资源加载协调和诊断。项目可以直接采用引擎或库已经提供的机制；Core 目录可以很小，甚至暂时没有自定义实现。

#### 2. 机制与业务的区别

| 可以是 Core 的责任 | 应由业务负责 |
| --- | --- |
| 调度存档读写、报告失败 | 作物和背包保存哪些字段 |
| 派发事件、解除订阅 | 达成何种条件才算任务完成 |
| 管理计时与取消句柄 | 某种作物生长需要多久 |
| 协调资源加载与释放 | 某个敌人使用哪种外观 |
| 通用对象缓存机制 | 哪种怪物何时出现 |

枪械、护甲、任务记录等专项兼容逻辑应由相应业务或项目迁移模块负责，不能成为通用存档机制中固定的分支。

#### 3. 接口与依赖

- Core 不导入具体 Package 的内部实现。
- 需要业务参与时，接受回调或公共接口，例如保存参与者；机制只认识约定，不认识作物和武器。
- Package 可以使用 Core 公共接口，不能依赖其内部实现文件。
- Core 之间也应有明确依赖，不能因为属于基础设施就允许循环。
- 不提供一个让所有代码随处查找任意业务对象的万能 Core。

#### 4. 实例与寿命

Core 不天然等于单例。一次会话、一个世界或一个测试可以拥有自己的机制实例。多个存档或世界同时存在时，不应共享不该共享的可变状态。

需要全局共享的只读配置、日志入口或引擎原生设施可以按项目规则共享；共享的范围和替换方式应明确。

#### 5. 错误和清理

资源加载、磁盘保存等可能失败的机制必须返回可判断的结果。不得仅打印错误后让业务继续认为成功。

监听、任务、缓存和资源句柄需要明确所有者与释放时机。调用 Stop / Dispose 多次时，不应重复保存、重复发奖或触发已清理对象。

#### 6. 避免两种过度设计

第一种是把所有业务都放入 Core，逐渐形成无法拆分的总控制器。第二种是为引擎每一个 API 都写一个只有一行转发的自建接口。

提取之前说明它实际解决的重复、替换或生命周期问题。若没有清晰收益，保留直接调用或普通工具函数即可。

### 数据与配置


#### 1. 数据默认由业务包拥有

种植包拥有地块和作物状态，背包包拥有容器与物品状态。数据可以是类实例、结构体、表、数组或引擎适合的对象。

通用规范不要求将数据统一挂载到玩家控制器、游戏状态对象或中央字典，也不要求每个数据类型先注册才能使用。

#### 2. 区分四类内容

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| 运行状态 | 随本次游戏变化的内容 | 已浇水、当前生命、任务进度 |
| 默认值与结构 | 新建状态时的起点及字段约束 | 地块默认未浇水，数量不得为负 |
| 配置 | 可由项目或策划调整的规则参数 | 生长天数、价格、冷却时间 |
| 稳定标识 | 持续指代同一概念的 ID | 作物 ID、物品 ID、事件类型 |

一份作物配置可被许多作物使用，但每株作物的生长进度不能写回共享配置。新建可变默认状态时必须产生独立实例，避免多个角色共享同一张默认表。

#### 3. Define 的作用

Define 可以包含领域类型、固定约束、默认状态创建和纯校验函数。它不负责启动服务、加载存档或发出玩法事件。

小型稳定配置可以和定义放在一起。只有出现策划编辑、覆盖、重载或来源管理需求时，才增加外置 Config。

#### 4. 配置进入业务的流程

```text
默认值与外部配置
    ↓
解析与明确的覆盖规则
    ↓
所属 Package 校验
    ↓
形成只读的有效配置
```

必须说明哪些来源优先，如何处理缺失和非法值。可以在非关键字段上回退默认值，也可以拒绝整条记录；选择应可观察，不能静默把非法配置变成意外玩法。

Config 不调用业务命令，不在读取价格时扣钱。校验所需的领域定义应能独立加载，避免“配置依赖定义、定义又初始化配置”的循环。

#### 5. 数据寿命

先按业务需要决定寿命：整个应用、当前游戏会话、当前世界、角色实例、场景或短期操作。项目只使用实际需要的范围，不要求全部建立对应管理器。

重要规则：

- 切换场景不应意外清空需要继续保留的业务状态。
- 结束会话不应让上一会话的异步结果写入下一会话。
- 同一游戏中的多个容器、地块或世界应有可区分的身份。
- 保存寿命可能长于运行对象寿命；需要时接入存档扩展。

“玩家数据 / 世界数据”是可用的业务分类，但不是客户端 / 服务端分类，也不自动决定保存和复制方式。

#### 6. 访问与修改

包外查询只获得需要的值或受控视图。修改通过拥有状态的包执行，保证其校验和副作用不会被绕过。

只读视图是否随内部状态变化、快照是否固定在查询时刻，应在需要时说明。不要把可以直接修改的内部表标注成“只读”后就认为边界已得到保护。

对于引擎中必须持有的资源或对象引用，明确它们是运行时引用及其有效期。需要保存时另行输出稳定 ID 和纯数据，而不是直接序列化整个运行对象。

#### 7. 不必提前加入的机制

没有跨会话保存需求时，不必引入 schemaVersion 和迁移链。没有多写入方或并发问题时，不必给每个字段附加版本号。没有统一观察需求时，不必每次修改都广播通用数据变化事件。

这些机制可以在需求出现后通过公开接口逐步增加，不改变“业务包拥有数据含义”的原则。

### 调用与事件


#### 1. 三种合作方式

| 需要 | 使用方式 | 示例 |
| --- | --- | --- |
| 获取结果但不改业务状态 | 直接查询 | 背包是否有足够容量 |
| 执行操作并判断结果 | 直接命令 | 放入物品、浇水、完成任务 |
| 通知多个关注者一个事实 | 事件或目标引擎的通知机制 | 作物已收获、任务已完成 |

Event 是一种可选通信方式；包只有一个明确调用者时，可以直接通过返回结果刷新界面，不必先搭建事件总线。

#### 2. 命令结果

简单命令可以使用枚举或语言常见结果类型，不要求所有函数套相同结构。结果必须足以让调用方区分它需要处理的情况。

```text
WaterResult:
  Watered          # 成功，状态改变
  AlreadyWatered   # 合法请求，状态不变
  PlotMissing      # 目标不存在
  NotWaterable     # 业务条件不允许
```

业务上预期的失败优先用可处理结果表达。异常用于意料之外的程序或环境故障，不能只捕获并忽略。

#### 3. 失败与一致性

单个命令尽量先验证全部条件，再执行修改。对外承诺“失败不改变状态”的命令必须符合这个约定。

一个批量操作可以选择全有或全无，也可以允许部分成功，但必须提前说明并返回具体结果。框架不要求所有命令都通过统一事务引擎。

多包合作时，协调者负责整体流程；各包仍负责自己的规则。同步、无重入的简单操作可以通过准备与提交完成；出现异步、并发或独立存储时，要增加适合实际需求的版本检查、预留或补偿机制，不能继续假设前置检查后状态永远不变。

#### 4. 事件规则

- 名称表达事实，例如 HarvestCompleted，不使用模糊的 DoSomething 代替命令。
- 事件在对应事实成立后发出，说明指内存提交还是已持久化。
- 发起方不依赖监听顺序或监听返回值决定原命令成功与否。
- 事件载荷优先使用身份和值，避免暴露可随意修改的内部状态。
- 谁订阅谁负责清理，或者由明确的拥有者统一释放。
- 监听回调发生错误时应记录并隔离，不伪造原操作未发生。

若某一步必须成功才能完成命令，它应是显式调用的流程步骤，不应藏在普通通知监听器里。

#### 5. 事件与依赖

订阅事件仍然依赖事件契约。契约可以由发布包公开，或在多个包共同使用时放入明确的共享契约位置。

不要通过 A 发事件要求 B 执行、B 再发事件要求 A 回答，绕过循环依赖检查。需要双方协调的业务应有一个明确的上层流程。

#### 6. 同步、异步与线程

本地纯计算保持同步即可。资源、磁盘和网络等长操作按引擎能力采用异步，并明确等待、取消、超时和结果归属。

异步回调必须检查目标上下文是否仍有效。界面关闭、场景销毁或会话替换后，不得继续写入失效对象。

需要主线程执行的引擎操作不能直接在任意后台线程调用。这属于引擎接入约定，不要求所有业务本身都理解线程调度。

### 依赖与生命周期


#### 1. 依赖必须看得见

可以通过语言模块导入、构造参数、初始化参数或明确的项目装配代码表达依赖。没有自动装配需求时，不强制额外写 Meta 文件重复记录同一事实。

允许 Package 依赖其他包的公开接口和 Core 公共入口，不允许依赖它们的私有实现文件。避免隐式全局可变对象成为无法追踪的依赖。

公开接口与共享常量可以被多方使用，但全局契约目录不能变成所有领域内部类型的集中堆放处。

#### 2. 手工装配是合法起点

```text
创建当前会话需要的机制
创建 Inventory 实例
创建 Planting 实例
连接收获流程
将公开接口交给 UI / 场景
开始运行
```

这里只有几个对象时，显式代码通常比扫描文件、解析元数据和生成索引更清楚。对象增多、目标组合变化或接入遗漏频繁时，再采用装配扩展。

#### 3. 最小生命周期责任

| 阶段 | 责任 | 是否每包都要实现方法 |
| --- | --- | --- |
| 创建 | 建立实例与私有状态 | 按语言和引擎正常创建即可 |
| 初始化 | 连接依赖、校验配置、读取必要状态 | 按需 |
| 开始 | 接收输入、注册监听、启动更新 | 按需 |
| 更新 | 执行确实需要逐帧或固定步长的逻辑 | 不需要就不注册 |
| 停止与释放 | 取消任务、解绑事件、释放资源 | 有所拥有的资源时必须处理 |

名称可以遵循引擎习惯。框架规定责任，不要求一套新的基类替代所有引擎回调。

#### 4. 初始化顺序

先准备被依赖的能力，再开放依赖它们的包。初始化失败时，不让使用它的界面继续提供必然失败的操作。

如果某个函数用于创建默认状态，它应能独立于监听注册和逐帧运行执行。启用存档时，数据恢复完成后才开放依赖该数据的业务。

重复触发生命周期事件时应有保护，避免重复订阅和重复启动计时。幂等不代表每次初始化都清空已有状态。

#### 5. 清理与场景切换

按照依赖的逆序停止相关对象。一个清理步骤失败时，尽量继续清理其余对象并报告错误。

场景对象只持有当前绑定；需要跨场景保留的业务实例由更长寿命的项目上下文拥有。框架不强制建立 Application / Session / World 全套类，只要求项目能说清这些对象何时有效。

销毁后将未完成任务标记为失效或取消，解除订阅，并阻止旧回调继续作用于新实例。

#### 6. 更新与性能

- 不为纯查询包或静态配置包添加空 Tick。
- 普通帧更新、物理更新、游戏时间推进按真实语义区分。
- 游戏暂停时哪些计时继续、哪些停止，由玩法说明。
- 允许事件驱动和批量更新，不要求所有实体都独立注册。

例如作物按“游戏日”成长，可以在推进一天时集中计算，不需要每帧扫描全部作物。

#### 7. 功能关闭

若项目提供可选功能，明确是在启动前选择还是允许运行中切换。基础规范默认不提供任意热卸载保证。

关闭功能前要处理依赖和引用；需要保留的数据不能因为入口隐藏而删除。正在运行的流程是否取消或等待结束，由具体扩展说明。

### 开发、测试与调试


#### 1. 开发步骤

1. 明确可观察行为和边界，例如“地块已浇水时再次操作不会重复消耗资源”。
2. 找到拥有该规则的 Package，先扩展已有职责，再判断是否需要新包。
3. 定义公开查询、命令结果和必要依赖。
4. 完成最小实现，不先创建没有需求的机制。
5. 验证成功、失败和生命周期边界，再接入真实场景。
6. 更新受影响的说明；使用生成扩展时重建并检查结果。

#### 2. 按风险选择验证

| 变化 | 合适的验证 |
| --- | --- |
| 纯规则和数据计算 | 独立于引擎的单元或公共接口测试 |
| 多包合作 | 集成测试，重点检查整体失败后状态 |
| 资源与场景绑定 | 引擎内运行和必要的人工交互 |
| 旧档兼容 | 固定旧档样本、迁移与失败恢复测试 |
| 网络命令 | 权限、重复、乱序、断线等对应测试 |
| 简单文案或目录调整 | 针对性的检查，不编写无实际价值的测试 |

不要求每个文件都配一个测试文件。测试应证明用户可观察行为和风险，不只是复制实现中的判断。

#### 3. 测试隔离

每个测试使用自己的业务实例和数据。随机与时间影响结果时，按需要注入可控来源，不要求所有生产代码先增加抽象接口。

测试不得依赖固定执行顺序或上一例残留状态。setup / teardown 出错应报告，失败和取消后也应尝试清理。

单 Case 默认清理；需要保留现场时使用明确的调试模式。没有断言或明确预期的测试不能静默算作有效验收。

#### 4. 等待与异步

优先等待明确条件并设置超时，避免用固定休眠掩盖时序错误。异步测试应覆盖对象释放后结果返回、取消和执行失败。

不要用真实玩家存档作为可随意覆盖的测试材料。存储测试使用隔离位置和固定样本。

#### 5. 调试信息

日志应能回答：哪个操作、哪个业务实例、输入是什么、失败在哪里、结果是否提交。必要时带对象 ID 和操作 ID。

不要求每个函数打印日志，不在每帧输出大量正常信息。涉及存档或账户数据时避免记录无关敏感内容。

调试命令可以创建场景和数据；测试负责断言；人工检查负责交互、画面和声音。三者可以合作，但不能互相冒充。

#### 6. 引擎测试与可移植性

业务测试通过只能说明规则在当前测试环境中成立。引擎接入还需要验证真实生命周期、资源和导出包行为。

若要证明跨引擎通用，至少在第二个目标环境运行同一组行为案例。不同语言可以有不同实现，但结果、失败语义和数据约束应一致。

### 评审与交付检查


本清单按实际改动使用。没有启用的扩展标记为“不适用”，不为了勾选清单而引入功能。

#### 1. 基础检查

- [ ] 业务责任有明确归属，没有让公共机制包含具体玩法分支。
- [ ] 包外调用公开接口，没有直接访问其他包的私有数据。
- [ ] 查询与修改可区分，命令结果和失败后状态明确。
- [ ] 新建可变状态不会与其他实例共享默认对象。
- [ ] 依赖可追踪，没有新增循环和隐式全局状态。
- [ ] 配置校验和非法值处理符合项目约定。
- [ ] 需要清理的监听、任务和资源有拥有者与释放时机。
- [ ] 有针对性的验证能覆盖本次改动的风险。

#### 2. 条件检查

| 本次涉及 | 检查内容 |
| --- | --- |
| 事件 | 事实成立后通知，清理订阅，监听不决定原命令返回值 |
| 多包修改 | 明确整体一致性，覆盖中途失败和可能重入 |
| 存档 | 数据版本、旧档恢复、保存失败和备份策略 |
| 中央数据管理 | 没有绕过拥有者的业务校验，没有未经约定的双写 |
| 自动装配 | 声明与实际依赖一致，缺失与循环可诊断，生成无漂移 |
| 联机 | 可信身份、执行端、可见性与重复消息处理 |
| 引擎接入 | 对象有效期、主线程要求、资源导出与实际运行 |
| 可选功能 | 关闭后引用可诊断，保存数据按约定保留 |

#### 3. 交付说明模板

```text
解决的问题：
最终行为：
公开接口或数据变化：
启用或调整的扩展：
验证结果：
已知限制与后续事项：
```

报告真实完成的验证，不把“生成成功”写成“玩法测试通过”，不把一份设计文档写成已有运行时实现。

#### 4. 不适用项示例

单机无存档的塔防原型，可以将存档、网络复制、存档迁移、数据注册和自动装配全部标记为不适用。它仍然可以完整遵循 Package / Core 的基础规范。

### 引擎接入原则


#### 1. 组织规则通用，接入方式遵循引擎

Package / Core 用于明确职责，不代替引擎已有的场景、组件、资源和生命周期机制。

项目使用何种引擎和语言，由实际开发需要决定。本框架不要求为复用 Lua 引入额外解释器，也不要求所有语言生成完全相同的文件结构。

#### 2. 哪些内容值得保持独立

优先让数值计算、物品规则、任务条件、种植进度等纯业务规则脱离场景对象。这样更容易测试，也更容易迁移。

UI、动画、物理、音效与场景交互可以直接使用引擎惯用结构。业务确实需要查询世界或发起资源操作时，可以由接入函数或小范围接口提供，不预先建立完整引擎替代层。

#### 3. 何时创建适配接口

满足以下实际需求之一再评估：

- 同一业务需要在两个环境运行。
- 外部副作用使规则测试困难，需要可替换实现。
- 多个业务需要统一的错误、取消或资源释放语义。
- 项目正在迁移引擎，确有需要保持稳定的业务契约。

没有这些需求时，集中、清晰的直接接入也可以接受。不要为每个引擎函数机械生成转发方法。

#### 4. 接入需要说明的内容

| 内容 | 项目应回答 |
| --- | --- |
| 启动入口 | 何处创建和连接业务实例 |
| 生命周期 | 何时开始使用、何时停止与清理 |
| 对象身份 | 引擎对象如何对应业务实体 |
| 资源 | 配置中的标识如何找到实际资源 |
| 线程与异步 | 哪些操作需主线程，如何取消迟到结果 |
| 保存 | 是否启用，使用什么平台能力 |
| 网络 | 是否启用，按什么架构执行 |
| 工具与导出 | 编辑器中有效的引用能否进入最终运行包 |

#### 5. 常见引擎方向

以下为接入建议，不代表本目录提供了对应实现。实际项目记录具体引擎版本并核对 API。

| 环境 | 接入建议 |
| --- | --- |
| Unity | 用必要的 MonoBehaviour 或启动对象连接生命周期；规则可使用普通 C# 类型，不要求每包一个组件 |
| Godot | 场景交互由 Node 承担，纯规则与可保存数据按需分离；不要求每包成为 Autoload |
| Unreal | 根据寿命、反射和复制需求选择 Actor、组件或其他宿主；不统一把状态挂在 PlayerController |
| 绿洲启元 | 保留有用的 Lua 组织与 UGC 接入，将宿主、复制和平台存档约定放在专用规范 |

Unity 的执行阶段、Godot 场景树回调和 Unreal 的游戏框架对象各有语义，不能仅把方法名字替换为 Initialize / Update 就认为生命周期完全一致。

#### 6. 验证跨引擎适用性

选择一个不依赖复杂表现的业务包，在两个目标环境中实现同一组成功、失败和数据恢复案例。

验收关注公开行为与数据约束一致，而不是内部目录逐字相同。原生资源、渲染和编辑器插件通常需要分别实现，不能把业务契约通用误写成整套工程可直接搬迁。
