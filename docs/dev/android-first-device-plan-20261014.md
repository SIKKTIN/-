### 闭馆门禁规则修正（2026-10-14）

用户确认：非开放时间门保持锁闭，室内有人或靠近门口不能使门自动打开；玩家持对应房卡可以主动刷卡开门。定时房间现在保留手动刷卡/关门结果，直到下一个开放时段边界再重置。无卡在锁闭房间内也不能免卡开门；宿舍宵禁与劳动管制仍保留看守放行规则。底层防夹只延迟尚未关闭的门，不再把已经锁好的门重开。房卡说明和门口文字同步更新为实际权限与“已锁（需房卡）/门已开”。

验证：闭馆门禁专项 18 项、完整房卡回归 123 项、棋牌日程 11 项、物件显隐 15,024 次对照通过。旧 `p127_full_body_doors.gd` 有 4 项失败；换回修改前的两处门关闭方法复测，失败项完全相同，记录在 `docs/tests/timed-card-lock/legacy-collision-baseline.json`，不宣称这份旧脚本整体通过。新专项另行覆盖已锁门不得被身体重叠重开、开门状态防夹和身体离开后关闭。

门禁规则修改尚未导出到新的 APK。证据：`docs/tests/timed-card-lock/checks.json` 和 `docs/tests/keycards-v1/checks.json`；入口已加入 `qa/regression_suite.json` 的 `timed_card_lock`。

### v0.2 复测与车间绘制优化

用户确认 v0.2 帧率有所提升，未再观察到 30 多 FPS，但进入“一号车间”后持续约 40 FPS，站立也不恢复，整体仍不稳定。

固定车间视角的 Windows Compatibility 对照发现：物件阴影贡献约 175 次绘制调用。将每个物件原有的多层阴影按原顺序合并为一个三角网格，保留形状、室内显隐、空间裁剪和叠加顺序。一号车间减少 140 次绘制调用，二号车间减少 84 次。无 HUD 的同场景一号车间对照为 665→525 次；有 HUD 的探索采样约 894→758 次，NPC 状态不同使两轮数值略有差异。没有把这个差值换算为手机 FPS。

Compatibility 与 Forward+ 共 12 组昼夜截图对照，最大颜色通道差均不超过 2/255（网格顶点颜色量化），人工检查未见明显视觉变化。物件显隐 15,024 次对照及绘制缓存回归通过。测试的无参数建筑材质共享没有减少绘制次数，因此未改入产品代码。电脑帧耗时受系统负载波动，不能据此承诺手机改善幅度。

已构建 `build/android/prison-android-arm64-release-v3.apk`，版本 `0.3-workshop-test` / versionCode 3，约 586.6 MiB，沿用旧包签名，可覆盖安装。签名、16 KiB 对齐、ARM64、资源完整性和版本检查通过，并核对包内阴影脚本字节码确已更新。证据位于排查目录中的 `workshop-summary.json`、`shadow-*`、`release-v3-*`。真机仍待用户复测，重点是在同一时段、同一视角进入一号车间后站立及移动时的持续帧率。

### 首轮手工反馈与性能排查（2026-10-14）

用户在 iQOO Z9 Turbo 手工安装首包后反馈：进入园区即频繁波动于约 50 FPS，进入房间会卡顿并降到 30 多 FPS；读数来自手机游戏侧栏。这不是“稳定 50 FPS”。没有 USB 连接，尚无设备端 CPU/GPU、热状态或帧耗时采样。

本轮在 Windows / RTX 4050 Laptop / Compatibility / 1600×720 下，用当前代码生成计时探针。模拟跨房间边界只验证可见性切换负载，不代替实际步行开门流程或手机性能。排查证据保存在 `docs/performance/android-frame-investigation-20261014/`。

已定位并修正三处重复计算：

1. 场景包含 626 个物件，进出房间曾逐一刷新其屋顶关系。现在缓存静态房间归属，普通进出只更新旧、新房间相关物件；地图布局、障碍状态或同房间其他可见性变更仍走完整同步。12 次边界切换的场景同步从 6.26～8.17 ms 降到 0.54～0.73 ms。
2. 门禁曾对远处 NPC 先做权限和房间判定，再判距离。现在先排除范围外 NPC，权限规则不变。同进程交替 CPU 测量由约 0.79 ms 降到 0.18 ms。
3. 棋牌交互每帧、多次扫描全部物件寻找牌桌。现在按物件版本缓存牌桌清单，地图重建时失效。同进程交替测量由约 0.38 ms 降到 0.006 ms。

以上全部是电脑端测量，不能换算为手机 FPS，也不能据此宣布手机稳定 60 FPS。车间视角仍有约 900 次绘制调用，绘制压力、安卓帧调度、第一次显现素材的 GPU 开销还需要真机继续定位。

回归证据包括：24 种房间状态共 15,024 次物件显隐与旧实现一致、牌桌缓存失效与返回值隔离、门禁 122 项、棋牌与日程 11 项。旧 `p78_visibility_regression.gd` 引用已不存在的 `routine_panel`，不能用于当前版本验收；使用本轮逐项显隐比较替代。探针中 `simulation_disabled` 旧报告的 `game_ms` 是停用前遗留值，不作为耗时证据；后续探针已在停用时清零。不同场景及分轮总帧时间只作探索性观察，未控制所有 NPC 状态与系统负载；同进程交替比较用于三个局部热点的 CPU 验证。

这些代码修改已于 2026-10-14 导出为 `build/android/prison-android-arm64-release-v2.apk`：版本 `0.2-perf-test` / versionCode 2，615,043,757 字节（约 586.6 MiB）。使用 Release 引擎模板，沿用原测试证书和包名，支持覆盖原测试包安装。签名、16 KiB 对齐、ARM64 架构、资源完整性、版本号和签名一致性检查均通过；Android manifest 未开启 debuggable。构建证据为排查目录中的 `release-v2-*` 文件。手机帧率仍待用户复测。

`build/android/prison-android-arm64-debug.apk` 保留为原始首包；请选择文件名含 `release-v2` 的新包。新包同时包含性能修复和 Release 模板，不能将复测收益全部归因于其中任一项。

第一轮使用用户提供的 iQOO Z9 Turbo，回答三个问题：现有园区是否能在 Android 正常呈现与操作；持续游玩是否出现明显内存增长、发热降频和卡顿；后续开发是否需要提前改变资源加载架构。

官方规格为骁龙 8s Gen 3、Adreno 735、12/16 GB RAM、2800×1260、20:9 屏幕。实际 RAM 容量、当前 Android/OriginOS 版本和 GPU 驱动在连接真机时记录，不以出厂系统版本推断当前系统。此机用于首台验证，不作为最低配置验收机。

| 阶段 | 工作 | 交付与完成条件 |
| --- | --- | --- |
| 1. 环境和设备 | 检查 SDK 版本、配置 JDK 17、安装匹配模板，添加 Android ARM64 本地测试预设；用户在手机开启 USB 调试并确认电脑连接 | adb 能识别已授权设备；记录实际机型、RAM、系统和显示设置 |

| 3. 渲染和触控对照 | 在相同资源、分辨率与帧率条件下比较 Compatibility 和 Mobile；检查昼夜、手电阴影、水面、墙体拼接、透明边缘、UI 安全区和多指输入 | 两组同场景数据和截图，选出画面正确且持续表现更好的方案；不预先承诺更换渲染器一定更快 |

| 5. 决策与开发基线 | 对照下面的标准决定通过、定点优化或架构调整 | 一份结论：采用的渲染器/纹理格式/画质、当前阻断问题、下一轮动作、尚未覆盖的机型 |

## 测试条件

- 固定 60 FPS 上限；记录系统刷新率，关闭或记录游戏插帧、超分等厂商增强，避免将显示帧率当成引擎帧率。
- 场景先以约 720 像素短边作为内部渲染目标，按设备宽高比布局。记录实际渲染目标尺寸；当前 `canvas_items` 拉伸下，仅修改设计尺寸不等于降低实际渲染分辨率。检查文字清晰度与触控坐标映射。
- 日常性能比较使用相同地图版本、起点、路线和环境设置，记录包与代码版本。Mobile/Compatibility 的对照先使用同一套双方支持的纹理，避免同时改变两个主要变量。
- 尽量不充电测试，固定亮度并记录室温、电量及系统性能模式；两轮间让设备恢复到相近热状态。不得绕过或关闭系统温控。
- 调试 APK 用于定位错误；性能结论以带轻量统计的本地 release 测试构建复核。正式发行签名和商店发布不属于本轮。
- 首次安装后的启动与结束进程后的再次启动分别记录，不把系统已缓存的启动称作严格冷启动。

1. 主菜单 → 加载 → 园区；检查首次进入、再次启动、暂停和重开。
2. 宿舍 → 车间 → 食堂 → 浴室/医务室 → 院落/设备区；检查进出室内、屋顶切换、墙门遮挡和快速拖动视野。
3. 左手摇杆配合右手互动；松手、切目标、打开背包、关闭弹窗、地图定位；确认没有重复执行或持续移动。
4. 打开背包、搜集、使用物品、商人交易和地图；检查细字、图标、屏幕挖孔与系统手势区域。
5. 正常速度跨越工作、用餐与夜间时段；检查 NPC 路线与集中寻路引起的卡顿。
6. 夜间手电、警犬、追捕和抓回；同时观察帧耗时与画面正确性。
7. 三次前后台往返，以及一次锁屏恢复；验证输入释放、暂停策略、音频和画面恢复。仅对进程仍存活时要求现场状态保持；系统回收后的继续游戏依赖后续存档能力，当前不可宣称支持。
8. 重复相同路线并回到同一状态，检查预热后内存是否持续上升。

教程遇到已有引导或地图阻塞时单独记录。可以用明确标识的测试入口继续性能采样，但不能据此宣称完整教程已通过。

## 首轮项目目标与决策

以下为本项目的暂定工程目标，不是 Android 的统一内存限制；获取首轮实测后按最低目标机重新校准。

| 指标 | 暂定目标/处理规则 |
| --- | --- |
| 功能和画面 | 安装、进入 R04、主要触控和关键界面可用；无崩溃、黑屏、花屏或缺图。此类问题必须先解决 |
| 稳态帧耗时 | 60 FPS 模式下目标 P95 ≤20 ms、P99 ≤33.3 ms；加载、切时段和追捕分别统计，不把长帧从总体记录中删除 |
| 持续性能 | 后十分钟相同场景不应相较前段出现持续明显降频；连续 >100 ms 卡顿和可感知的反复顿挫需定位 |
| 纹理内存 | 中期预算 150～250 MiB；第一轮先测真实格式和占用。超过预算先定位大贴图、重复引用和整图常驻资源 |
| 进程内存 | 先以约 600～800 MiB 的 Total PSS 作观察目标，加载峰值单列；渲染统计和 PSS 分开记录，不直接相加，不以设备有 12/16 GB 就判定通过 |
| 内存趋势 | 预热后，相同往返循环回到同状态仍持续上涨需排查；增幅超过约 10% 是排查信号，不单凭一次增幅判定泄漏 |
| 进入游戏 | 从点击开始到可操作目标约 12 秒内；全过程有及时反馈，单列首装首次启动 |
| 后台恢复 | 三次往返无黑屏、卡住、输入残留；完整存档另列工作包 |

记录 Android `dumpsys meminfo` 的 PSS/RSS/Graphics 分类、引擎纹理统计和帧耗时分布；系统热状态优先，电池温度不能冒充芯片温度。没有设备端数据时不填写“通过”。

决策规则：

- 功能/资源格式/触控有阻断问题：先修复再继续扩大内容。
- 功能正常，只有显存/内存偏高：优先调整手机贴图分档；仍超预算再做当前区与相邻区的纹理预加载和释放。NPC、碰撞与作息逻辑继续运行。
- 内存可接受但作息切换卡顿：单独优化 CPU 寻路或调度，不用继续压图代替分析。
- 该机通过：继续游戏开发，并保留这一组真机回归。后续增加一台较低配置 Android 手机后，再制定最低配置承诺。
