R04 性能优化实施计划
依据：2026-10-12 performance-report.txt 及对应原生计时数据。
状态：已完成本轮生产优化与回归验收；详见 ../p137/performance-result.txt。剩余偶发长帧按报告记录，未宣称所有帧稳定60fps。

目标和约束
在当前地图、人物数量、美术效果和玩法规则下，降低最坏帧耗时，改善 60fps 的稳定性。
保持玩家手动操作、NPC 独立生活、9–12/14–17 工作、15 分钟一天、搜索与背包交互。
保留用户保存的地图编辑结果。每阶段只处理对应热点，完成对照验证后再扩大改动范围。
修复顺序：失败寻路 → 重复更新 → 素材载入 → 静态绘制 → 呈现与综合验收。
零星 148–158ms 未归因长帧从第一阶段起持续记录，不等到最后才检查。

开始前：固定基线与复现环境
1. 记录当前生产源文件、R04 数据和资源清单的哈希，保存可恢复的改动前快照。
2. 沿用 p136 原生测量，计时覆盖主循环、HUD、动态绘制、渲染 CPU/GPU（引擎支持时）。
3. 保存完整帧间隔和 >20ms 长帧上下文：时段、角色位置、目标、路径结果、障碍修订号、绘制次数、纹理占用。
4. 重复测试采取 A/B/A 同一场景、相同种子和窗口尺寸；记录背景程序与机器运行状态。
5. 分开报告：启动/首次进入、预热后的运行、60fps 限速的等待时间、解除限速的工作耗时。

第一阶段：消除不可达目标的重复重搜索（最高优先级）
修改范围：world_navigation.gd、workshop_overseer.gd，必要时修正明确错误的监工巡逻配置。

实施：
1. 复现已捕获的两个坐标组合，检查实际门禁和两套网格的连通性，确认监工为什么滞留。
2. 为各角色规则使用的网格建立可达区域索引。只有当前有效索引证明不连通时才快速拒绝。
3. 连通索引依据实际阻挡和对角规则构建；初次计算在载入期完成，障碍变化后及时失效。
   门变化后的重建需要增量或分帧完成，不能把寻路尖峰换成索引重建尖峰。
   索引尚未更新时不使用旧结果错误拒绝路线。
4. 缓存由静态拓扑证明的失败结果，键包含网格/通行规则、起终点区域及障碍修订号。
   因另一角色临时挡路而失败的结果采用短期重试，不能当成永久不可达。
5. 对静止且不可达的巡逻点退避重试或按规则跳到下一个有效点；门开启、目标移动等事件立即重新评估。
6. 将搜索请求排队并错开 NPC 重算。单次同步 AStar 仍可能超时，不能把排队误当成真正耗时上限。
   若可达复杂路线仍超预算，再增加局部搜索/分步搜索；线程方案须使用独立网格快照，避免共享网格被动态覆盖。
7. 对可达长路线与失败路线比较 JPS 开关，按实测选择；不凭一个失败案例全局切换。

验证：
已知失败点反复尝试、长路线、两种门口网格、门开关、推箱、人物临时挡路、监工巡逻与追捕。
特别检查门打开后恢复走动，不出现穿墙、困在原地、追捕延迟或错误认定不可达。

验收：
已知失败点查询目标 <1ms，不再每 0.3 秒出现 36–47ms 搜索。
工作时段持续原生采样不再出现这类 40ms 以上脚本尖峰。
记录可达路线的最坏耗时，不能通过略过有效追捕来满足指标。

第二阶段：建立每帧一次的系统更新职责
修改范围：game_frame.gd、prison_schedule.gd、room_access.gd、gate_watch.gd。

实施：
1. 主循环统一执行门禁与门岗角色更新；作息负责时钟、阶段变化及必要的状态通知。
2. 移除作息与主循环的重复 tick，保留初始化、读档/切图、开发工具改时钟、跳过夜晚时的显式同步。
3. 阶段变化先同步门禁状态再行动，防止 9/12/14/17 点发生一帧错误通行。
4. blocking 等状态仅在确有角色/门禁/技能变化后重新计算；必要的立即响应仍保留。
5. 对本次实际热点整理职责和函数接口，避免为优化重写全部项目架构。

验证：
更新次数计数、起床、上下班、门口有人时关门、逃班追捕、禁闭释放、暂停恢复、跳夜和教程。
复用现有作息/门禁/工作人员流动测试，对新增职责边界补充针对性验证。

验收：
正常帧门岗角色行动只更新一次，重复门禁检查被消除。
同场景 CPU 主逻辑耗时下降，所有时段行为与工资/体力累计正确。

第三阶段：按实际依赖加载素材，分开运行和编辑目录
修改范围：game_presentation.gd、world_texture.gd、prop_catalog.gd，以及编辑器缩略图加载。

实施：
1. 建立 R04 依赖清单，涵盖墙体、摆设、开关门状态、组合纹理、屋顶、地面、角色动画与 UI。
2. 运行时加载当前依赖及别名最终目标，停止无条件加载全部历史 architecture_ 定义。
3. 编辑器保留完整素材选择目录，缩略图按可见分类/页加载并缓存，避免打开工具一次加载全部高清图。
4. 收紧纹理缓存生命周期，检查同一母图/裁剪区域重复占用；明确共享资源与图内资源的所有权。
5. 清理文件前建立引用检查，区分运行依赖、编辑素材、概念稿和 QA 证据。
   先停止无用载入，再处理确认无引用的缓存/临时资源；历史别名和用户地图素材继续保留。

验证：
所有当前房间、门的两种状态、背包/搜索/拖放、全素材目录、切图、退出重进和连续编辑。
美术大小、清晰度、透明边缘及色彩不发生退化。

验收：
当前地图运行不再载入确认未用的历史母图，纹理统计低于约 670MiB 基线。
公布实际释放量、启动耗时和首次访问长帧，而非承诺未经核算的内存降幅。

第四阶段：按空间区块合并静态绘制
修改范围：static_ground.gd、scene_layers.gd，依据实测再涉及 world_volume.gd。

实施：
1. 优先合并可共用材质的静态墙阴影、地面标记；先试 256/512 世界单位的区块大小并比较。
2. 保留区块包围盒供屏幕外裁剪，避免全地图合并后失去裁剪收益。
3. 家具拖动、门开关只刷新受影响区块；人物、活动门与推箱保留动态绘制和正确遮挡排序。
4. 对屋顶/室内可见性保持分区开关。只有确实需要逐物排序的对象继续单独绘制。
5. 节点数量和绘制提交分别统计；合并节点不保证批处理成功，须验证实际 draw calls。

验证：
同视点截图对比、墙连接、门口遮挡、室内外切换、地图编辑器拖动/撤销、屏幕外裁剪和阴影接缝。

验收：
以同视点约 810 次提交为基线，争取降低至少 25%，并验证渲染耗时确实下降。
保持现有美术和遮挡效果，不能通过关闭阴影或少画场景达标。

第五阶段：长帧归因、帧调度与最终验收
1. 持续检查非寻路的 148–158ms 长帧：区分其他节点、渲染命令构建、纹理首次访问、驱动等待和系统调度。
2. 对照独立运行、Godot 编辑器运行；必要时验证发布构建，计时工具不写入发布版。
3. 比较 60fps 限速的 VSync 开/关与解除限速；确认显示器刷新率和实际帧间隔后再调整呈现策略。
   不盲目叠加帧率上限和 VSync，不通过提高 FPS 数字掩盖输入卡顿。
4. 运行寝室/车间/仓库/庭院/外围移动、巡逻/追捕、搜刮与双向拖放、地图编辑器操作。
5. 至少运行一个完整正常速度游戏日（15 分钟），覆盖时段切换；另做七天状态循环验证。
   加速七天测试验证状态正确性，不作为正常速度 FPS 的证明。

最终性能目标（本机 1200×720，预热后）
解除限速的帧间隔 P99 ≤16.67ms；60fps 模式 P99 ≤20ms，避免可重复的游戏计算长帧。
主逻辑每帧耗时与寻路耗时单独公布，记录 >20/33/50ms 帧数量和原因。
若仍有未归因或依赖外部调度的长帧，列出证据与剩余问题，不以平均 60fps 宣布解决。

交付
每阶段提供修改范围、同场景前后测量、针对性验证和剩余风险。
保留生产改动与计时工具的边界，整理生成文件到诊断目录。
全部阶段完成后提交一份最终性能报告和回归结果。
